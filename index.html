Dynamic instrumentation toolkit

Reprogram running software, from the app down to the kernel.

Frida puts your code inside live processes and operating system kernels. Hook any function, trace private code, rewrite behavior, and see the result the moment you hit save. No source, no recompile, no restart.

Where it runs

Three ways in.

Pick the vantage point the target allows. Everything above it, from the scripting API to frida-trace and Luma, stays the same.

Injected

frida-core

Attach to a running process, or spawn one with your hooks in place before its first instruction. frida-core does the injecting, from inside your own tool on the machine you are on. On a remote device it runs headless as frida-server, so a frida-core elsewhere can reach it. frida-portal fronts a whole fleet the same way, exposing the processes that have joined it.

How injection works

As a library

frida-gadget

No root or jailbreak? Frida injects Gadget into a debuggable iOS or Android app for you. Elsewhere, preload it with LD_PRELOAD or DYLD_INSERT_LIBRARIES, load it from your own test runner, or repackage an app with it when you want custom tweaks baked in. It waits for you to connect, or runs scripts on its own from the filesystem.

About Gadget

In the kernel

frida-barebone-agent

Load the Barebone agent into the operating system kernel. Instrument the kernel itself and every process above it, from one session, with nothing left for the process to detect. No kernel to speak of? Barebone drives microcontrollers and custom kernels over a GDB remote stub, with no agent on the target at all.

Meet Barebone

Barebone

An agent that lives in ring 0.

Barebone is Frida's bare-metal backend. Its agent is written in Rust around the same GumJS engine that runs inside user processes, so the API you already know now works against a kernel. Where there is no kernel to host it, the same API works over a debug stub alone.

Getting it in

Through a GDB remote stub
QEMU, VirtualBox, Parallels and the Android emulator all expose one. So does a hardware debugger, which puts a physical device's kernel in reach over JTAG or SWD.
As a driver
On Linux and Android, insmod frida-agent.ko. On macOS, load the agent as a kernel extension. Then ask frida-core for the barebone device, from the CLI or the API. add_barebone_device() on the DeviceManager takes options, and FRIDA_BAREBONE_CONFIG points the default device at a JSON config. Only tools on another machine need a frida-server --device=barebone in between.
Or with no kernel at all
A microcontroller, a bootloader, or a custom kernel with no room for an agent: point Barebone at its GDB remote stub and your script runs on the host instead. Memory access such as readU32() becomes a stub read, and Interceptor with JavaScript callbacks becomes a software or hardware breakpoint. Hand Interceptor a NativePointer instead and it places an inline hook in the target's memory, usually code you built with RustModule, the Barebone runtime's counterpart to CModule.

What you get

Kernel and user mode, together
Enumerate processes, attach, spawn with instrumentation in place, hook functions, query the kernel's BTF types, and watch kernel modules come and go. From the kernel, the agent injects into user processes itself.
Invisible from inside the process
The kernel half cloaks the user-mode agent's threads and memory mappings. Runtime application self-protection looking from inside the process finds nothing to see.
Light on memory
User-mode agents map the same physical pages the kernel agent already uses. Each instrumented process allocates only its own writable portion.

Languages

JavaScript is the fast path, not the only path.

Most people start with a few lines of JavaScript because the edit, save, see loop takes seconds. The rest of the stack speaks whatever you do, on the host and inside the target.

Interceptor.attach(Module.getGlobalExportByName('recvfrom'), {
  onEnter(args) {
    this.fd = args[0].toInt32();
  },
  onLeave(retval) {
    console.log(`recvfrom(fd=${this.fd}) => ${retval.toInt32()} bytes`);
  }
});

The agent side

This runs inside the target, in a process or in a kernel, on QuickJS or V8. Write it in TypeScript if you like, with autocompletion from the bundled type definitions. Hot paths can drop into C with CModule.

No JavaScript required

The frida crate wraps frida-core for the host side. Build a static binary that drives devices and sessions without a Python or Node runtime anywhere near it.

frida-rust on GitHub

use frida_gum::{Gum, Module, interceptor::*};

struct Log;
impl InvocationListener for Log {
    fn on_enter(&mut self, ctx: InvocationContext) {
        println!("recvfrom(fd={})", ctx.arg(0));
    }
    fn on_leave(&mut self, _ctx: InvocationContext) {}
}

let gum = Gum::obtain();
let mut interceptor = Interceptor::obtain(&gum);
let recvfrom = Module::find_global_export_by_name("recvfrom").unwrap();
interceptor.attach(recvfrom, &mut Log).unwrap();

The hooks themselves, in Rust

The frida-gum crate exposes Interceptor, Stalker and the rest of Gum directly. Compile your instrumentation into a shared library and inject it, link it into your own program, or run it inside Gadget. No script engine in the loop.

For developers

Debug the build you already shipped.

Logging has blind spots, and you find them in the field. Instead of redeploying a special build just to see more, build a tool on Frida that attaches to the software your customers are already running.

Look anywhere, after the fact

Hook the function that the logs do not cover, inspect its arguments, and change what it returns, on the process that is misbehaving right now. No new build, no restart, no lost state.

One tool, every version

Resolve symbols, offsets and types at runtime, so a single product-specific tool supports the versions out in the field. That is more elegant than a tracing feature per release, and it ages better.

In-house or in-product

Keep the tool external and leave the product untouched, or ship Gadget inside your own software as a first-party inspector. Build it in Python, Rust, Swift or Node.js, or as a Luma workspace your whole team shares.

Quick start

Up and running in seconds.

One pip install gives you frida-trace, the REPL, frida-ps and friends. Point them at a local process, a phone over USB, or a kernel. Full quick-start guide

$ pip install frida-tools
$ frida-trace -i "recv*" Twitter
recvfrom: Auto-generated handler: …/recvfrom.js
Started tracing 21 functions.
1442 ms  recvfrom()
# Live-edit recvfrom.js and watch the magic!
5374 ms  recvfrom(socket=67, buffer=0x252a618, length=65536, flags=0, address=0xb0420bd8, address_len=16)
# Kernel running under QEMU with its GDB stub on? That is the default: 127.0.0.1:3333.
$ frida-ps -D barebone
# Loaded frida-agent.ko or the kext instead? Point the default device at it.
$ FRIDA_BAREBONE_CONFIG=barebone.json frida-ps -D barebone
# Attach to the kernel, or to any process, with frida, frida-trace, or Luma.
# Scripts see kernel modules, kallsyms, and BTF types alongside the usual Gum APIs.
# Tools on another machine? Run frida-server --device=barebone there and connect as usual.
